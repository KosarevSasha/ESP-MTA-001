# МТА — v0.4.13 Test LOAD + FIFO Delivery

Основа: испытанная v0.4.12. **Тестовая версия, не предназначена для коммерческой эксплуатации.** `main` не менялся.

## Что добавлено
Команда **заглавная `D`** в Serial Monitor (115200, No Line Ending) теперь регистрирует одну **физически добавленную** банку `DOBRY_COLA_025`. Действие возможно только при:
- `SERVICE`, открытой сервисной двери (не запускать во время продажи);
- наличии сигнала датчика следующей банки;
- исправной NVS, свободном месте в FIFO и отсутствии текущей передачи или блокировки синхронизации;
- полностью завершённой платёжной сессии, отсутствии финансовой неопределённости;
- корректных часах NTP (первоначально подключить Wi-Fi).

Успешная `D`: единым защищённым механизмом `appendStockEvent()` пишет `LOAD` +1 в NVS, увеличивает локальный остаток на один, формирует уникальный следующий ID; CommunicationManager самостоятельно отправляет событие на VPS. Удаление из NVS только по `HTTP 200` и правильному ID со статусом `accepted` / `already_accepted`.

**D НЕ проверяет индивидуальный Data Matrix, не гарантирует фактическое добавление банки и НЕ заменяет дальнейший учёт «Честного знака».** Оператор обязан сначала положить одну банку, затем ввести `D` **один раз**. Не нажимать D повторно после ошибки без анализа `I` и `L`: операция могла уже сохраниться.

### Установка
1. Скачать **всю папку v0.4.13**, а не один `.ino`; рядом с `.ino` должны быть `PaymentManager.h`, `PaymentManager.cpp`, `mta_tls_ca.h`.
2. Скопировать локальный рабочий `mta_secrets.h` из v0.4.12 (не передавать на GitHub).
3. Arduino IDE: ESP32 Dev Module, COM3 если актуален; Verify, затем Upload. **Не стирать NVS / Erase All Flash**.
4. До LOAD: `Q`, `I`, `L`; ожидается IDLE/PM=IDLE, stock=0, 0/64, HTTPS heartbeat 200. Серверный остаток по панели 0. Перед тестом рекомендуется свежая резервная копия SQLite на VPS.

### Один контрольный LOAD 0→1
1. Убедиться, что ESP32 и терминал запитаны, связь с VPS восстановилась и время установлено.
2. **Физически поместить одну банку** в механизм. Открыть сервисную дверь и убедиться, что контроллер находится в `SERVICE` (проверить `P`), датчик `next_can` = PRESENT.
3. Отправить **один раз** `D`. Ожидаются `[MTA EVT] SAVED ... type=LOAD`, `[MTA LOAD] SAVED ... local_stock=1`.
4. Отправить `I`, `L`: если интернет доступен, событие может уже уйти и очередь быть 0/64; при отсутствии интернета оно должно остаться в FIFO.
5. Дождаться `[MTA NET] Event ... HTTP=200 confirmed=1`, `[MTA EVT] CONFIRMED ... remaining=0`.
6. На панели MTA Monitor убедиться, что остаток сервера 0→1. Для полного подтверждения базы можно отдельно проверить event_id в SQLite.
7. Закрыть сервисную дверь, убедиться, что нормальная готовность восстановлена. Не запускать реальную покупку вне согласованного демонстрационного режима.

**Ожидаемый следующий ID при сохранённой истории последней продажи №5: `MTA-001-E0000000006`.** Если иной, не перезаписывать вручную: проверяем журнал.

## Проверено ранее на реальном оборудовании (v0.4.12, 15.11.2026)
- Демонстрационная продажа при наличии интернета: событие #4, ESP 2→1, VPS 2→1, HTTP=200, очередь опустела.
- Демонстрационная продажа во время недоступности интернета: событие #5, ESP 1→0, при HTTP=-1 сохранено в NVS, после восстановления связи HTTP=200 confirmed=1, остаток VPS 1→0, запись в MTA Monitor, очередь 0.
- Серия без предъявления карты: завершение без продажи и изменения остатков.
- Для **v0.4.13** все испытания ещё ожидают подтверждения на устройстве; только исходный код размещён в GitHub.

## Неисследованные риски
- Отказ питания при записи NVS, неопределённые исходы финансовой операции и массовая нагрузка.
- Резко растущие `UART invalidLength`/`discarded`: расследовать отдельно, несмотря на успешный платёжный обмен.
- Wi-Fi `wifi:sta is connecting, cannot set config`: отдельная доработка.
- QR/Data Matrix «Честный знак», инвентаризация, фискализация, реальные платежи вне деморежима — отсутствуют/не проверены.
- Не изменять `main` до ревизии с Романом.
