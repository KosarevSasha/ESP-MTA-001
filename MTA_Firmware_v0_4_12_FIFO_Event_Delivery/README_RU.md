# WANT!PAY!TAKE! — v0.4.12 FIFO Event Delivery — лабораторная интеграционная сборка

## Назначение
Основа — v0.4.11. Автоматическая FIFO-доставка подтверждённых событий **LOAD / SALE / ERROR_SET / ERROR_CLEAR** на VPS с сохранением в NVS, HTTPS-авторизацией и повторной отправкой после сетевого сбоя. Изменения только в экспериментальной ветке; main не тронут.

## Отличия от v0.4.11
- Убрана жёсткая привязка отправки к `MTA-001-E0000000003`. Поддерживаются следующие номера событий.
- Сервер принимает SALE с `product_id=DOBRY_COLA_025`, `price=100` (копеек), `payment=SUCCESS`, `dispense=SUCCESS` и уникальным session_id в формате event_id. Отправка SALE допускается только после перехода из DISPENSING в SUCCESS, а не при простом касании кнопки.
- Входящая финансовая авторизация остаётся ответственностью PaymentManager/Vendista. Симулятор оплаты и фальшивое `PAYMENT_APPROVED` **не добавлены**.
- Перед новой оплатой проверяются исправность NVS, отсутствие `stockop`, наличие места в журнале и отсутствие заблокированной доставки.
- При успешном HTTPS ответе только с `accepted` или `already_accepted` и совпадающим `event_id` запись признаётся сервером. Неуспех сохраняет событие. Ответ HTTP 4xx переводит отправку в блокировку до анализа; сбой сети / 5xx допускает повтор.
- Команда `D` для ручной искусственной загрузки отключена во избежание неучтённых операций; позднее её заменит сканирование Data Matrix. TEST, если он окажется в начале FIFO, не отправляется: его надо отдельно обработать / архивировать через прежний диагностический `A`.
- Локальный остаток сохраняется через stockop + NVS после штатно подтверждённой физической выдачи. Перезапуск ESP не должен обнулять очередь или остаток.
- Обновлено название папки, .ino и строка запуска v0.4.12.

## ВАЖНО: испытания
**Это всё ещё тестовая сборка, не готова к платным продажам.** Компиляция на Arduino IDE и работа с реальным Vendista до сих пор не проверены для v0.4.12; логика платежей, возвратов и кассовых чеков должна быть испытана отдельно. Никаких реальных транзакций до выполнения фискальных требований.

1. Скопировать в новую папку локальный `mta_secrets.h` из проверенной v0.4.11. Пароли и ключи не отправлять в GitHub.
2. Выбрать ESP32 Dev Module, правильный COM, Verify. При успешной сборке Upload **без Erase All Flash**.
3. Serial Monitor 115200: ожидается `Firmware v0.4.12 FIFO Event Delivery starting`; наблюдать HTTP=200. Команды `I`, `L`, `Q` — только чтение. Текущий ожидаемый остаток `2`, журнал `0/64`.
4. Проверить на VPS отдельным read-only запросом: товар `DOBRY_COLA_025` = 2, события #2 и #3 зарегистрированы ровно по одному разу. Перед любой операцией, изменяющей остаток, создать свежую резервную копию SQLite.
5. Испытание механики с сервисной выдачей **не равно продаже**: сервисная выдача не должна создавать SALE, и инвентарь от неё автоматически не меняется. Для учёта физически извлечённых при сервисе банок потребуется отдельная корректировка/инвентаризация.
6. Следующий интеграционный тест SALE проводится только при допустимой тестовой оплате после проверки регистраций и терминала, а также схемы фискализации; проверить успешную оплату, физическую выдачу, подтверждение VendReport, локальное уменьшение 2→1, запись SALE, HTTPS-подтверждение и серверный остаток 2→1.
7. Для отключения сети тестировать временную потерю Wi-Fi при **неизменном питании ESP32**; следить, чтобы события оставались в журнале при HTTP=-1, а после восстановления связи доставлялись без дублирования.
8. В любой непонятной ситуации **не стирать NVS, не повторять платёж и не исправлять SQLite вручную**. Зафиксировать исходные Q/I/L и журнал сервера, затем разбирать.

## Ограничения, которые остаются для дальнейшей работы
- Учет по индивидуальным Data Matrix «Честный знак», инвентаризация, операция корректировки отсутствуют.
- Не завершены испытания питания ESP32 от ПРП, настоящей оплаты, отмены/возврата, отключения питания в середине NVS-операции и самовосстановления после неопределённой финансовой операции.
- В SALE сервер передаётся цена настройки платы, а не отдельная подтверждённая терминалом сумма из финансового отчёта; потребуется дополнительная сверка.
- При ошибке записи NVS после физической выдачи невозможно отменить факт выдачи; такой случай требует остановки эксплуатации и ручной сверки.
- Штатное перемещение v0.4.12 в main только после регрессионного тестирования и согласования с Романом.
